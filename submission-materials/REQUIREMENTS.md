# Handbook requirements and delivery boundaries

Source: `[Full Stack Developer] AI Interview Handbook FT (Updated as of Febuary 2026).docx`, read from the supplied Downloads/caprae folder, including its hyperlink relationships.

## Required deliverables

| Requirement | Submission material |
| --- | --- |
| Analyze SaaSquatch features and business model | Product rationale and research in application documentation |
| Engineer one or two impactful features within five hours | Lead quality review and explainable prioritization; application source |
| Detail UX choices | README and architecture documentation |
| Explain backend, database, caching, performance, hosting, deployment, provider, and exact stack | Architecture and deployment documentation; distinguish implemented behavior from proposed hosting |
| GitHub repository with code, setup, and permissible dataset | Local source repository and synthetic fixture data; publication requires an available authenticated GitHub account |
| One to two minute video explaining choices, value, and results | Walkthrough material and demo artifact |
| Optional notebook or API demonstration | Runnable API and documented demonstration |
| Three business answers, each no more than three to four paragraphs | BUSINESS_RESPONSES.md |
| Work status, 40-hour availability, salary, and employment confirmations | Explicit applicant fields in BUSINESS_RESPONSES.md |
| Up-to-date resume | Applicant must provide their actual current resume; none supplied |
| Email with specified role and name subject | EMAIL_DRAFT.md; not sent |
| Reapplicant answers if applicable | Conditional section in BUSINESS_RESPONSES.md |

## Scope and claims

The application is an independent assessment prototype, not an integration with the authenticated SaaSquatch application. Public product information was reviewed; authenticated behavior and the linked video could not be verified. Synthetic data is safe to distribute and must remain clearly labeled. No revenue, deliverability, sales conversion, or acquisition outcome is represented as measured from real customers.

Applicant identity, work authorization, salary, resume, and agreement to employment terms cannot be inferred from a Windows username or location. These must remain explicit fields until the applicant supplies the facts. The software and supporting materials can be completed independently of them.

Research and drafting are separate from the handbook's five-hour engineering budget. Actual development duration and known limitations should be recorded honestly in the application documentation.
